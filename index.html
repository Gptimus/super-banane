1

Le site tourne sur le laptop du dev

1× Laptop

Le développeur a codé la boutique : catalogue, panier, commande. Tout marche, sur son ordinateur.

Problème

Il ferme son laptop : le site disparaît. Personne ne peut plus acheter.

Solution

Installer le site sur une machine faite pour rester allumée en permanence.

Essaie
Le site répond.

Anecdote : à ses débuts avec Zip2, Elon Musk codait la nuit et laissait son PC servir le site pendant la journée. Possible, mais pas fait pour durer.

2

Un serveur dans un datacenter

1× ServeurLaptop retiré

Un serveur est un ordinateur normal : processeur, RAM, disque. Il est plat pour s'empiler dans une baie et conçu pour ne jamais s'éteindre. Dans la plupart des cas, l'histoire s'arrête là.

Problème

Le bouche-à-oreille marche. Plus de visiteurs simultanés, c'est plus de charge. Aux heures de pointe, le site ralentit.

Solution

Plus de puissance. Deux façons : une machine plus grosse (scaling vertical) ou plus de machines (scaling horizontal).

Monte le curseur « Charge » sous la planche : l'étiquette du serveur passe au jaune puis au rouge, et des requêtes tombent en rouge.

Charge maximale de ce montage : –

3

Scaling vertical : un serveur plus costaud

1× Gros serveurPetit serveur retiré

Plus de cœurs, plus de GHz, plus de RAM. Aucune ligne de code à changer.

Choisis le processeur

Limite 1 · plafond

Une fois le plus gros CPU installé et tous les slots de RAM remplis, impossible d'aller plus loin. Même le plus riche du monde ne peut pas acheter une machine infinie.

Limite 2 · prix

Si un 8 cœurs coûte environ 200 €, un 16 cœurs coûte plutôt 500 à 800 € que 400 €.

4

L'application d'un côté, la base de l'autre

1× Serveur app1× Base de données

Sur la machine tournent deux programmes : l'application (le code du dev) et la base de données (stocks, commandes, utilisateurs). Ils se disputent le même CPU et la même RAM.

Solution

Un serveur pour l'application, un serveur pour la base. Chacun profite de toute sa machine.

À surveiller

Une base de données est du code bas niveau très optimisé. Le goulot d'étranglement, c'est presque toujours l'application : son pourcentage monte en premier.

Charge maximale de ce montage : –

5

Plusieurs serveurs et un load balancer

1× Load balancer+3× Serveur app

Au lieu d'une machine plus grosse, on en ajoute d'autres. Chacune sert une partie des clients. Plus de visiteurs ? On ajoute des serveurs, tant que la carte bancaire passe.

Problème

Impossible de dire aux clients « toi, va sur banane-serveur-2.com ». Il faut une seule adresse : superbanane.com.

Solution

Un load balancer (répartiteur de charge) reçoit toutes les requêtes et les distribue. Il ne lit pas leur contenu : il consomme environ 100 fois moins qu'un serveur applicatif, qui doit authentifier, calculer, interroger la base. Un seul peut alimenter des dizaines de serveurs.

6

Plusieurs load balancers, répartis par le DNS

1× DNS+2× Load balancer

Passage à la télé, viral sur TikTok : le load balancer reçoit à son tour trop de requêtes. Pire, c'est un single point of failure : s'il tombe, les 50 serveurs derrière ne servent plus à rien.

Solution

En mettre deux, trois, puis plus. Le DNS de superbanane.com répond plusieurs adresses IP ; le navigateur en choisit une et s'y connecte. Les clients se répartissent entre les load balancers.

$ dig +short superbanane.com
203.0.113.10
203.0.113.11
203.0.113.12

Fais l'essai avec youtube.com : plusieurs IP reviennent, et elles changent d'une requête à l'autre.

Ajoute des serveurs
À surveiller

Regarde la base de données : elle reçoit les requêtes de tous les serveurs, jour et nuit. C'est elle, le nouveau point faible.

Charge maximale de ce montage : –

Copier la base ne suffit pas : il faut la découper

+2× Base de données

Les serveurs applicatifs sont stateless : on peut en redémarrer un, une requête peut tomber sur le 3 ou le 5, rien ne change. La base est stateful : elle contient les données, et chaque commande doit être visible partout.

8

Un primaire pour écrire, des réplicas pour lire

1× Primaire4× Réplica

Sur la plupart des sites, 90 à 95 % des requêtes sont des lectures : catalogue, historique de commandes. Les écritures (nouvelle commande, nouveau produit, nouveau compte) restent rares.

Solution

Un serveur primaire reçoit seul les écritures et les recopie vers des serveurs secondaires en lecture seule. L'application lit sur n'importe lequel ; les réplicas n'ont pas besoin de se parler.

Règle les lectures et écritures
LectureÉcritureSynchronisationPerdue
Limite

Ça tient tant que les écritures restent rares. Pousse la part d'écritures vers 30 % : le primaire sature. Restent alors le scaling vertical du primaire, le sharding et d'autres techniques.
